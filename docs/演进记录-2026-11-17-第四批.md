## 本批完成清单

### 1. 合规勾选 UI 接入在线版 client

**现状**：第三批已在服务端建好可信声明通道（`AgentRunCreateRequest.rights` 随加密 body 提交）+ 留痕，但在线版 client 的 `createRun()` 仍固定发送明文头 `X-Rights-Confirmed: true`——该头不在加密 AAD 内、可任意伪造，服务端只能标 `plaintext_header` 兼容留痕。完整勾选组件只存在于离线桌面端 `web/`，在线版用户从未真正采集 basis/note。

**改动**：
- 新增 `client/src/components/ComplianceGate.vue`：参考改编提交前的模态确认，采集 `basis`（own/authorized/public_domain）、权利确认、AIGC 知情两个必勾项、选填备注。确认返回结构化 `RightsDeclaration`，取消返回 null；解锁滚动、Esc 关闭、卸载释放等待中的 Promise。
- `client/src/types.ts`：`CreateRunPayload` 加可选 `rights?: RightsDeclaration`，basis 枚举与服务端 `RightsDeclaration` 完全对齐（含 `public_domain`，不是桌面端的 `public`）。
- `client/src/utils/rightsDeclaration.ts`：抽离声明构造纯逻辑（`canConfirmRights` / `buildRightsDeclaration` / basis 白名单），node 环境可单测；note 去空白、空串转 null 与服务端 `Optional[str]` 对齐。
- `Home.vue::submit()`：参考改编在上传/建单前先 `await rightsGate.ask()`，用户取消则直接 return（不上传、不建任务）；声明写入 payload 随加密 body 提交。
- `agentApi.ts::createRun()`：移除可伪造的明文头，只保留 `Idempotency-Key`；权利声明唯一可信来源为 `payload.rights`。
- 单测 6 个（两个必勾项门控、结构固定 true、note 归一、非法 basis 回退、枚举对齐）。

**效果**：新客户端的权利声明进入加密 AAD，服务端审计 `source=encrypted_body`、可强校验 basis 与 AIGC 知情；明文头路径只作为旧客户端兼容回退保留在服务端。

### 2. 失败重试指数退避（next_retry_at）

**现状**：第二批给 `execute_task` 加了有限重试，失败后立刻 `status=queued`，RQ worker 在同一轮 `run_task_job` 末尾立即 `enqueue_task` 重投——瞬时失败会以秒级密集冲击抖动中的上游，且 SQLite/低配部署下形成空转。

**改动**：
- `Task` 模型 + 迁移 `n3f4a5b6c7d8e`：新增 `next_retry_at`（可空 UTC 时间）+ 索引 `idx_tasks_retry_due(status, next_retry_at)`；`alembic check` 零漂移。
- `config.py`：`task_retry_backoff_seconds=5`、`task_retry_backoff_max_seconds=300`。`services/tasks.py::retry_backoff_seconds(attempts, settings) = min(base * 2^(attempts-1), cap)`，含下限保护。
- `execute_task` 失败重试分支写入 `next_retry_at = now + backoff`（用注入的 `now`，可测）；原子认领 SQL 增加 `(next_retry_at IS NULL OR next_retry_at <= now)` 条件并认领时清空该字段——未到点绝不双跑。
- 终态/取消/手动重排路径统一清 `next_retry_at`，避免残留退避阻塞运营操作。
- **调度侧**：`scheduler.py::dispatch_retry_due()` 扫描 `queued AND next_retry_at <= now`，清字段并回流 task_id 交给事务后 `enqueue_task` 重投；加入 `run_once` phases（常驻 scheduler 每 60s 一轮，5s 起的退避最多晚一个调度周期生效）。
- **worker 侧**：`run_task_job` 遇 `queued` 但退避未到点时跳过立即重投（否则每秒空转重投）；本地 `run_once` 查询也过滤未到点任务。
- 单测 5 个（指数增长+封顶、失败写退避时间、未到点不认领、scheduler 到点触发/未到点不触发）。原重试用例改为推进模拟时钟越过退避点。

**权衡**：RQ 3.x 原生延迟队列在本仓库未启用（compose 只跑 `rq worker`，无 `--with-scheduler`），故选用「DB 存到点时间 + 现有常驻 scheduler 轮询」方案——不引入新进程/新依赖，重复投递由原子认领兜底无副作用。

### 3. 前端错误上报转发 Sentry

**现状**：第二批建好 `POST /v1/telemetry/client-error`（匿名、脱敏、限流、结构化日志），服务端也配了 `sentry_dsn` 与 `init_sentry()`，但两条链路互不相通——浏览器异常只落本地日志，进不了 Sentry 聚合。

**改动**：
- `services/sentry.py::client_error_to_sentry()`：入参是 telemetry 已脱敏字段；DSN 为空/SDK 未装/SDK 抛异常都静默返回 False，绝不影响上报响应；不传用户身份，只带匿名 tag（source/client_path/error_code）与 `source_request_id` extra。
- `api/telemetry.py`：脱敏后调用转发，指标改为单次计数并打 `forwarded=yes/no` 标签（避免双重计数）；响应恒为 202 空语义体。
- 单测 3 个（配置 DSN 转发脱敏内容、无 DSN 不调 SDK、SDK 异常不影响响应）；用 `sys.modules` 注入假 `sentry_sdk`，测试环境无需真实安装 SDK。

## 坑与回归说明

- **client lint**：项目脚本 `eslint .` 为 0 error（4 条 warning 均为未触碰的既有文件），加 `--max-warnings=0` 会假性失败，按项目脚本口径验收。
- **全量 pytest**：一次并发运行（两个 pytest 进程同时跑）曾出现大批 `AssertionError` 级联（fixture 层相互干扰）；串行重跑干净退出 0。结论：全量测试必须串行，避免并发共享 fakeredis/临时目录状态。
- **alembic 连库**：`server/.env` 的 DATABASE_URL 指向未启动的本地 Postgres，迁移检查用 `DATABASE_URL=sqlite:///.alembic_check.db` 覆盖；Windows 下必须用相对路径（`$(pwd)` 的 Git Bash 路径 Windows Python 无法打开）。
- **worker 空转**：若只在 DB 写 `next_retry_at` 而不改 `run_task_job` 的重投逻辑，会形成「RQ 立即重投→认领被拒→再重投」的秒级空转；本批 DB 到点 + worker 跳过 + scheduler 触发三处同时改才闭环。
