### 1. 契约扩面（subscriptions / tasks / runs）

前八批已覆盖 crypto / healthz / genres / plans / entitlements / audit / providers / notifications / push-subscriptions，本批把三组稳定接口纳入 response_model。

**subscriptions（6 路由）**：
- `POST /v1/subscriptions`、`GET /v1/subscriptions/current`、`POST .../cancel`、`.../resume`、`.../renew`、`.../upgrade` 全部声明契约。
- 新 schema：`SubscriptionPlanView` / `SubscriptionView`（含 `renewal_reminder: bool | None`）/ `PaymentIntentView`（`params: dict[str, Any]`）/ `OrderView`（`meta: dict[str, Any]`）/ `CreateSubscriptionResponse` / `CurrentSubscriptionResponse`（`renewal_reminder: bool` 必出）/ `SubscriptionActionResponse` / `RenewSubscriptionResponse` / `UpgradeSubscriptionResponse`（`payment` 可 null）。
- 关键差异：`current` 顶层多一个 `renewal_reminder` 布尔；其余接口由 response_model 补 `renewal_reminder=null`，前端类型改为 `boolean | null`。
- `/orders` 两个接口本批未纳入（返回结构与订阅族共用 `OrderView`，但下单列表动态字段多，留待后续）。

**tasks（4 路由）**：
- `POST /v1/tasks`、`GET /v1/tasks/{id}`、`GET /v1/tasks/{id}/logs`、`POST /v1/tasks/{id}/cancel` 全部声明契约。
- 新 schema：`TaskView`（19 字段，`params: dict[str, Any]` 原样保留权利声明 / source_key / aigc_label 等运行时参数）/ `CreateTaskResponse` / `TaskDetailResponse` / `CancelTaskResponse` / `TaskEventView` / `TaskLogsResponse`。

**agent-runs（只覆盖固定结构的 7 路由）**：
- 声明契约：`POST /agent-runs`、`POST .../cancel`、`.../pause`、`POST .../cover`、`.../cover/upload`、`DELETE .../cover`、`DELETE /agent-runs/{id}`。
- 新 schema：`CreateAgentRunResponse` / `AgentRunActionResponse` / `AgentRunCoverResponse`（`cover` 动态 dict 不裁剪）/ `AgentRunCoverDeleteResponse` / `AgentRunDeleteResponse`。
- **刻意不契约化**：`GET /agent-runs` 列表、`GET /agent-runs/{id}` 详情、`PATCH` 更新、`resume`（返回 `run_to_dict` 的 30+ 动态字段，强契约会裁剪 outline / chapters / review / options / cover 等）、SSE events、封面二进制流、产物下载。保留 dict 返回以守住「动态字段零裁剪」的既有约束。

**测试与类型**：契约测试新增 3 个（订阅 6 路由 $ref + 运行时 params/meta 不裁剪 + current 补 bool、任务 4 路由 + next_retry_at/log 事件字段集、运行固定路由 + 动态详情/列表/SSE 显式无 $ref），契约测试总数 13→16。client `types.ts` 同步：`CreateRunResponse` 补 `enqueued` / `created` 必出、`created_at: string | null`；`Subscription.renewal_reminder: boolean | null`、`provider: string | null`。两端 typecheck 通过，定向回归 71 passed。

### 2. Web Push 投递回执与失效订阅清理（410/404 自动退订）

**问题**：第八批已有 `getattr(exc, "status_code", None) in (404, 410)` 的雏形，但用伪异常测试、没有真实状态码区分、无逐订阅回执、下线不写 `updated_at`、全失效仍走无意义重试。

**改动**：
- `services/webpush.py` 新增 `error_status_code(exc)` / `is_expired_subscription_error(exc)`，用 `frozenset({404, 410})` 明确失效语义；非 HTTP 异常（密钥错误 / 网络故障）无 status_code，不会被误清理。
- `services/notifications.py` push 分支重构：逐订阅生成 `receipts`（`sub_id` / `status` / `error`，有 HTTP 码时加 `http_status`），`delivery.meta` 增 `expired`（下线订阅 id 列表）与 `receipts`；失效订阅写 `status="expired"` **且刷新 `updated_at`**。
- 状态码分层：仅 404/410 自动下线；429/5xx / 网络异常保留订阅、delivery 走退避重试。
- 全订阅失效时改为 `status="skipped"` + `reason="all_subscriptions_expired"`，不再写 `next_retry_at` —— 重投也只会命中 `no_active_subscription`，避免无效重试。部分成功仍记 `sent`（防止给成功设备发第二遍）并记 `last_error`。
- 测试：改写原失效用例为真实 `pywebpush.WebPushException`（带 response.status_code），新增 404 下线、429/500/503 保留订阅（参数化）、无 status_code 异常不误清理、多订阅混合回执（410 + 成功）5 组共 6 测试；通知测试总数 10→16，全过。

### 3. 去重 zset 容量上限

**问题**：第七/八批的滑动窗口 zset 在时钟回拨或旧版本遗留数据下可能膨胀，缺成员数保险丝。

**改动**（`services/sentry.py` + `tests/test_telemetry.py`）：
- 新增 `_DEDUPE_MAX_ENTRIES = 64` 常量与 `_dedupe_in_redis(..., max_entries=...)` 入参；`should_forward` 增 `dedupe_max_entries` 可选入参，默认用常量（防御性保险丝，不进后台可配链路，避免为运营调参改动 7 处）。
- 裁剪用 `ZREMRANGEBYRANK key 0 -(cap+1)`（负数索引含端点，`-(cap+1)` 才恰好保留 cap 条；cap=1 写 `-2` 不会误删刚写入的成员）。
- 插入位置：add 路径放进 `WATCH/MULTI` 事务内与 `zadd` / `expire` 原子提交；reject 路径仅在 `seen > cap` 时发一次裁剪（历史超限 key 自愈，正常路径仍纯读）。
- 设计澄清：正常滑动窗口 add 路径只写 1 条（score 清理已先删旧点），超限只来自时钟回拨 / 遗留数据，因此裁剪主要发生在 reject 路径。
- 测试新增 5 个（3 + 参数化 3 计为 5 函数/用例）：膨胀 key 命中去重时裁到最新 3 条且 TTL 保留、reject 路径自愈、cap=1/5/64 全覆盖且最新条目不误删。遥测测试 17→22 全过。
