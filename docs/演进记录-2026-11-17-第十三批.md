## 1. 契约扩面（reconcile / quota / presets / payments）

`server/app/schemas.py` 新增稳定出参契约：

- 对账：`AdminReconcileReportView` / `AdminReconcileReportsResponse`
- 额度调整：`AdminQuotaAdjustmentView` / `AdminQuotaAdjustmentsResponse` / `AdminQuotaAdjustResponse`

  `InvoiceListResponse` / `AdminInvoiceListResponse`

加 `response_model` 的路由（保留 `items` + 旧别名 `refunds`/`invoices` 双字段，前端平滑过渡）：

- `admin.py`：`GET /reconcile-reports`、`GET|POST /accounts/{id}/quota-adjustments`、

- `payments.py`：`GET /refunds`、`GET /invoices`、`GET /invoices/{id}`、
  `GET /admin/refunds`、`GET /admin/invoices`、`GET /admin/invoices/{id}`（共 6 处）
- `presets.py`：`GET /presets`、`POST /presets`（共 2 处）

约定：`summary` / `meta` 等由业务演进的动态 JSON 用 `dict[str, Any]` 保留，不被契约裁掉。
契约测试 `test_openapi_contract.py` 新增 4 条，核对 14 个路由的 `$ref` 与组件 schema 存在。

**全量回归抓到并修复的隐藏分支**：`POST /quota-adjustments` 的幂等命中分支只返回
`{"duplicate": True, "event_id": ...}`，而初版 `AdminQuotaAdjustResponse` 把字段全设为必填，
导致该分支触发 `ResponseValidationError`（4 个 missing）。这正说明契约扩面的价值——暴露了
单测没覆盖的真实分支。修复：`adjustment/audit/before/after` 改为可选（默认 None），
并在 `test_admin_ext.py` 补断言锁定幂等响应字段边界。

## 2. Web Push 批量推送与回执历史

**后端**（`schemas.py` + `api/admin.py`）

- `POST /v1/admin/notifications/batch`：一次提交多个 `account_ids`（1–200）共享标题/正文/渠道。
  - 共享 `batch_id`，但每账号独立 `dedupe_key` 与投递记录，互不覆盖；
  - 单账号不存在或 emit 异常不拖垮整批，逐条返回 `status: sent/skipped/invalid_account` 与原因；
  - 全批一个事务提交，写 `notification.batch` 审计。
- `GET /v1/admin/notifications/{delivery_id}/receipts`：把 `delivery.meta` 的逐订阅回执拆成
  稳定结构（订阅 ID / 状态 / HTTP / 建议退避 / 错误 + 送达汇总），便于跨投递对账与后续导出。
- 契约：`AdminNotificationBatchRequest/Response`、`BatchNotificationResultView`、
  `PushReceiptView`、`PushReceiptHistoryView/Response`。
- `admin.py` 补 `logger`（批量单账号失败告警）。

**前端**（admin）

- `api.ts` 加 `sendNotificationBatch()` / `notificationReceipts()`；`types.ts` 加对应类型。
- `Alerts.vue`：页头加「批量发送」弹层（账号 ID 解析去重、渠道勾选、逐账号结果展示），
  push 渠道行加「回执」按钮打开结构化回执历史弹层。

测试 `test_notifications_batch.py`（5 条）：逐账号投递与 dedupe 独立、账号去重幂等、非 admin 403、
回执结构正确、缺失投递 404。

## 3. 可观测配置灰度生效

**设计**：灰度按**错误指纹稳定分桶**——同一错误永远走基线或灰度档中的同一档，不在两者间抖动。
灰度档只覆盖显式配置的字段，其余回退基线值。

**后端**

- `runtime_config.py`：
  - `telemetry_defaults` 增 `canary_percent=0` / `canary={}`（不改 DB 结构，复用 `OperationalSetting.value` JSON）；
  - `_sanitize` 校验 `canary_percent`（0–100）与 canary 三项（各自范围，非法剔除、未知键忽略）；
  - 新增纯函数 `effective_for_bucket(cfg, bucket_key)`：`sha256(key)[:8]` 取模 100 分桶，
    `< canary_percent` 走灰度档，否则基线；空 key / 0% / 空灰度档全部回退基线；
  - `set_telemetry_config` 增可选 `canary_percent` / `canary` 参数。
- `api/telemetry.py`：上报时按 `fingerprint` 调 `effective_for_bucket`，用生效后的三项配置做采样/去重决策。
- `schemas.py`：`TelemetryCanaryView`，`TelemetryConfigView` / `Update` 加 `canary_percent` / `canary` 字段（可选）。
- `api/admin.py`：`PUT /telemetry-config` 透传灰度参数并写审计。

**前端**（admin）

- `types.ts` 加 `TelemetryCanary` 并扩展 `TelemetryConfig`；`api.ts` 扩展 `putTelemetryConfig` 参数。
- `TelemetryConfig.vue` 新增「灰度发布」区：开关 + 比例 + 三项灰度覆盖值（留空回退基线），
  保存时组装 canary 载荷；读回时回填灰度表单。

测试 `test_telemetry_canary.py`（8 条）：无灰度/关闭/全量、部分字段覆盖、分桶稳定性、
空 key 回退、非法值剔除、admin 更新回显。

`.env.example` 说明灰度为 DB 配置项、按指纹分桶，无对应环境变量。
